📘 Production-Grade EKS CI/CD Platform
1. Project Objective

Design and implement a production-ready cloud-native backend system deployed on AWS EKS with:

Infrastructure as Code (Terraform)

Automated CI/CD pipeline

Secure container build and deployment

Horizontal scaling

Observability with metrics dashboards

Zero-downtime rolling deployments

The system must simulate real-world DevOps/SRE practices, not a tutorial demo.

2. High-Level Architecture

Developer Push → GitHub Actions → Docker Build → Push to ECR → Helm Deploy → EKS Cluster → ALB → Users
Metrics → Prometheus → Grafana

5. Phase-Wise Implementation Plan
Phase 1 – Application Layer
Objective

Build a simple REST API that simulates order processing.

Requirements

Endpoints:

GET /health → returns 200 OK

GET /ready → checks DB connectivity

GET /orders → returns mock data

GET /metrics → Prometheus metrics

Other requirements:

Structured JSON logging

Graceful shutdown handling

Environment-based configuration

Expose port 8080

Acceptance Criteria:

App runs locally

App connects to PostgreSQL

Health and readiness endpoints behave correctly

Phase 2 – Containerization
Objective

Create a production-ready Docker image.

Requirements:

Multi-stage build

Minimal base image

Non-root user

Expose port 8080

Healthcheck instruction

Small image size

Acceptance Criteria:

Image builds successfully

Container runs locally

No root user inside container

Phase 3 – Infrastructure (Terraform)
Objective

Provision production-grade AWS infrastructure.

Requirements:

Networking:

VPC across 3 Availability Zones

Public + Private subnets

NAT Gateway

Proper route tables

EKS:

Private endpoint enabled

Managed Node Group

OIDC provider enabled

IAM roles using least privilege

State Management:

Remote backend (S3)

DynamoDB state locking

ECR:

Private repository for app images

Acceptance Criteria:

Terraform apply provisions working EKS cluster

kubectl can access cluster

Nodes are in Ready state

Phase 4 – Kubernetes Deployment
Objective

Deploy application using Helm.

Requirements:

Deployment:

2 replicas

Resource requests and limits

Liveness probe

Readiness probe

Rolling update strategy

Service:

ClusterIP

Ingress:

AWS ALB Ingress Controller

Internet-facing ALB

Config:

ConfigMaps for app config

Kubernetes Secrets for DB credentials

Acceptance Criteria:

App accessible via ALB DNS

Rolling update works without downtime

Pod restart does not break service

Phase 5 – CI/CD Pipeline
Objective

Automate build and deployment.

Trigger:

On push to main branch

Pipeline Steps:

Checkout code

Install dependencies

Run lint

Run unit tests

Build Docker image

Scan image (Trivy)

Push image to ECR

Update Helm image tag

Deploy to EKS

Run smoke test

Security:

Use GitHub OIDC for AWS authentication

Do NOT use static AWS credentials

Acceptance Criteria:

Push to main automatically deploys new version

Failed build blocks deployment

Phase 6 – Scaling & Reliability
Objective

Demonstrate SRE capabilities.

Requirements:

Configure HPA (CPU-based scaling)

Install Cluster Autoscaler

Add PodDisruptionBudget

Simulate traffic spike

Simulate pod failure

Acceptance Criteria:

Pods scale up under load

Pods scale down after load

Deployment survives node drain

Phase 7 – Monitoring & Observability
Objective

Implement full observability.

Install:

Prometheus

Grafana

Requirements:

Metrics to monitor:

CPU usage

Memory usage

Pod restarts

HTTP request count

HTTP latency

Create:

Custom Grafana dashboard

At least one alert rule

Acceptance Criteria:

Metrics visible in Grafana

Alerts trigger under failure condition

6. Engineering Constraints

No manual AWS console configuration

Everything must be reproducible via Terraform

No hardcoded credentials

Follow least privilege IAM

Follow Kubernetes best practices
